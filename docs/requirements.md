# 校园活动管理系统 V1.0 需求

## 1. 业务问题

校园活动的信息发布和报名如果依赖线下通知或分散渠道，组织教师难以统一发布活动和掌握报名情况，学生也缺少统一了解与参与活动的入口。V1.0 只建立可运行、可验证的基本业务闭环，不追求功能数量。

## 2. 用户故事

- **US-01 注册与登录：** 作为校园活动系统用户，我希望注册账号、选择学生或教师身份并登录，以便使用对应角色的功能。
- **US-02 教师创建并发布活动：** 作为活动组织教师，我希望创建活动、完善草稿并发布，以便学生了解和参与活动。
- **US-03 学生浏览活动：** 作为学生，我希望查看当前已发布活动及其详情，以便判断是否参加。
- **US-04 学生报名活动：** 作为学生，我希望报名满足条件的活动，以便获得参与资格。
- **US-05 学生管理自己的报名：** 作为学生，我希望查看自己的报名并在允许条件下取消，以便管理参与计划。
- **US-06 教师查看和管理已发布活动：** 作为活动组织教师，我希望查看本人活动的报名情况并关闭活动，以便掌握参与情况并结束报名业务。

## 3. 正式需求与验收依据

| 编号 | 用户/角色 | 需求描述 | 优先级 | 验收依据 |
|---|---|---|---|---|
| REQ-01 | 用户 | 用户可以注册并选择 `STUDENT`/`TEACHER` 角色，之后登录和退出系统 | Must | 注册成功；用户名唯一；密码哈希保存；登录后进入对应角色页面；未登录不能进入业务页面 |
| REQ-02 | 教师 | 教师可以创建、编辑、删除 `DRAFT` 活动，并将合法草稿发布 | Must | 草稿可编辑、删除；合法活动可发布；教师不能管理他人活动；发布后不可编辑、删除 |
| REQ-03 | 学生 | 学生可以浏览 `PUBLISHED` 活动并查看详情 | Must | `PUBLISHED` 可见；`DRAFT`/`CLOSED` 不出现在普通列表；满员或截止活动仍可查看但不可报名 |
| REQ-04 | 学生 | 学生可以报名满足条件的活动 | Must | 仅学生可报名；活动须为 `PUBLISHED`、未过截止时间、未满员且未重复报名 |
| REQ-05 | 学生 | 学生可以查看自己的报名，并在允许条件下取消 | Should | 只能查看、取消自己的报名；`PUBLISHED` 且未过截止时间时可取消；取消后释放名额并允许重新报名 |
| REQ-06 | 教师 | 教师可以查看本人活动的报名人数、学生名单，并关闭 `PUBLISHED` 活动 | Should | 只能查看本人活动报名；关闭后变为 `CLOSED` 且不能再报名；教师不能代替学生增删报名 |

## 4. 关键业务验收规则

- 系统仅有 `STUDENT` 和 `TEACHER` 两类角色；未登录用户不能访问业务页面，不同角色不能访问对方业务页面。
- 教师只能管理自己创建的活动；资源所有权必须由 Service 层再次验证。
- 活动状态只能按 `DRAFT -> PUBLISHED -> CLOSED` 转换；已发布活动不可编辑或删除。
- 活动标题、描述和地点非空，容量大于 0，并满足 `registrationDeadline < startTime < endTime`。
- 报名要求活动已发布、未截止、未满员且学生未重复报名；重复报名同时由 Service 检查和数据库联合唯一约束保护。
- 学生只能取消自己的报名，且活动必须仍为 `PUBLISHED` 并未超过报名截止时间。
- 教师只能查看报名、关闭本人活动，不能代报名、移除学生或审批报名。

## 5. 范围控制

V1.0 明确不实现：管理员、活动审核、真实统一身份认证、搜索、分类、筛选、推荐、评论、点赞、收藏、通知、邮件、短信、签到、二维码、报名审批、教师代报名或移除报名学生、Excel 导出、前后端分离、Vue/React、JWT/OAuth、Redis、Docker、消息队列、微服务以及复杂 UI 和动画。

这些能力不影响“发布—浏览—报名—查看结果”闭环成立，引入它们会扩大权限、状态、页面和基础设施范围，因此留待后续版本评估。
